# T1 优化分析

这份文档把 T1 定义为“可复现的 PyTorch/Transformers 基线加上低风险的推理路径优化”。T1 的目标不是提前实现所有高阶 kernel，而是先建立可信的正确性、计时边界和性能证据，避免后续优化建立在错误的比较上。

## 约束和判断标准

FAQ 规定模型固定为 `Qwen2.5-7B-Instruct`，不能蒸馏、裁剪或修改权重；FP16 贪心解码要逐 token 一致；所有推理要在 DCU 上完成。性能比较应多次运行并取中位数，核心指标是并发吞吐。Datawhale 教程还建议同时观察 TTFT、TPOT、P99、峰值显存，并把 prefill 和 decode 分开分析。

因此每个候选方案都按下面顺序判断：

1. 模型、输入 token、EOS、解码策略和 dtype 满足同一个 contract。
2. 正确性集逐 case 比较 token；FP16 不允许出现差异。
3. warmup 不计入成绩，正式运行保留每次原始数据，报告中使用中位数。
4. 只有在相同 batch、相同输入和相同计时边界下，吞吐提升才有意义。

## 当前基线的边界

`baseline.py` 预先 tokenize，使用左侧 padding 和显式 `attention_mask`，调用 `model.generate` 做 greedy decoding，并在设备同步后计时。模型加载、tokenize、文本 decode 不计入计时；生成出的 EOS 计入输出 token。默认 batch 按数据集原顺序组成，`--length-bucket` 才启用长度排序。

结果 JSON 现在同时记录：

- 有效输入 token 数 `input_tokens`；
- 静态 batch 实际送入模型的 token 数 `padded_input_tokens`；
- 补齐 token 数 `padding_tokens`；
- `padding_waste_ratio = padding_tokens / padded_input_tokens`；
- 每次运行的输出 token 吞吐、请求吞吐和峰值显存。

## T1 内最值得验证的算法点

### 1. 长度排序和分桶

对于长度为 `L_i` 的请求，一个 batch 的 prefill 计算近似按

```text
batch_size * max(L_i)
```

执行，而有用计算只有 `sum(L_i)`。因此可以先按输入 token 长度稳定排序，再按固定 batch size 切分。`baseline.py --length-bucket` 已实现这一策略，并在生成后按原始索引恢复结果顺序。

先做全局排序作为上界，再做固定宽度分桶，例如把长度限制在 `[0, 256]`、`(256, 512]`、`(512, 1024]` 等区间内。在线服务不能无限等待凑齐同桶请求，所以实际系统要在“长度相近”和“排队等待时间”之间取折中。T1 只测静态离线 batch，不把动态调度伪装成官方成绩。

用 `padding_waste_ratio` 判断分桶是否真的减少了无效计算；如果浪费已经很低，继续优化排序不会带来明显收益。

### 2. KV cache 消融

`use_cache=True` 是生成的正确基线。可用 `--no-cache` 做消融，记录相同输入下的 token 一致性和吞吐差异。没有 cache 时，每生成一个 token 都可能重新计算完整前缀，复杂度随生成长度快速增加；cache 让 decode 每步只追加当前 token 的 K/V。这个实验用于证明 cache 的收益，不应把关闭 cache 的结果作为优化方案。

### 3. Prefill/decode 分项计时

端到端 `generate` 只能告诉我们总耗时，不能判断瓶颈在长 prompt 的 prefill 还是逐 token decode。开发阶段可以增加手写 greedy loop，记录：

- TTFT：首个新 token 产生前的时间；
- prefill 时间和输入 token/s；
- TPOT：首 token 后每个新 token 的平均时间；
- decode token/s 和总耗时。

手写 loop 必须与 `generate` 做 token-level 对齐后才能用于性能分析。正式成绩仍以组委会定义的接口和边界为准。

### 4. Attention 实现和精度

当前 AMDGPU 实验表明 SDPA 比 eager 更快，因此 T1 应先固定 `attn_implementation=sdpa`，再单独比较 eager。BF16/FP16 的选择要以正确性集为门槛；不能只看显存或吞吐。FlashAttention、RMSNorm/MLP 融合属于 T2，不能在 T1 报告中与基线混为一谈。

## 实验矩阵

第一轮只改变一个变量：

| 组别 | batch | 输入长度 | attention | cache | 分桶 | 目的 |
| --- | --- | --- | --- | --- | --- | --- |
| B0 | 1/2/4/8/16/32 | 512 | eager | on | off | 原始参考 |
| B1 | 同 B0 | 512 | SDPA | on | off | attention 消融 |
| B2 | 同 B0 | 混合长度 | SDPA | on | on | padding 优化 |
| B3 | 1/8/32 | 256/1024/2048 | SDPA | on | on | 长度和并发敏感性 |
| B4 | 1/8 | 512 | SDPA | off | off | KV cache 消融 |

每组先 warmup，再至少运行 5 次；保存原始 JSON、commit、环境信息和命令。对离线批处理，主要看 output tokens/s；对交互式服务，还要看 TTFT 和 P99。若 B2 的吞吐提升来自减少 padding，应同时看到 `padding_waste_ratio` 下降。

## 不要提前塞进 T1 的内容

vLLM continuous batching、PagedAttention、INT8/INT4、prefix cache、投机解码、KV 压缩、自研 Triton/HIP kernel 都会改变调度、数值路径或部署栈。它们分别对应 T3/T4，应该在 T1 contract 和 profiling 结果稳定后再做。量化还要区分权重存储精度、激活精度和真实低比特 kernel，不能只把权重转换成低精度就宣称完成量化优化。

## 运行示例

```powershell
.venv\Scripts\python baseline.py --tiny --batch-size 4 --output results\t1-order.json
.venv\Scripts\python baseline.py --tiny --batch-size 4 --length-bucket --output results\t1-length.json
.venv\Scripts\python evaluate.py results\t1-order.json results\t1-length.json
```

上面的 tiny 命令只验证排序不会改变输出顺序。真实实验必须换成 DCU 上的本地模型、正确性集和官方评测集，并分别保存 baseline 与 candidate；不要把两个不同 batching 策略的结果直接当作不同模型进行比较。
