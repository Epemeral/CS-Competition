# T4 实施计划

T4 可以和 T1 并行推进。T1 负责固定模型、正确性和官方吞吐口径；T4 负责在已知热点上做 Triton/HIP 算子、融合和新解码路径。两条线共用同一个 token-level correctness contract，但不共用未经验证的性能结论。

## T4 的目标

T4 不是“写出一个 kernel”就结束，而是完成下面闭环：

```text
找到热点 -> 写 PyTorch 参考 -> 写 Triton/HIP 版本 -> 数值对齐
       -> 单算子中位数 -> 接入真实模型 -> 端到端吞吐/显存 -> 可复现实验
```

只有单算子和端到端都通过，才把它列为最终方案。单算子加速不能直接乘到模型总吞吐上；真实收益受该算子占比、kernel launch、编译缓存和调度影响。

## 现有工作台

`kernels/` 已经具备：

- `src/reference.py`：RMSNorm、融合 Add+RMSNorm、SwiGLU、RoPE、QKV 切分参考实现；
- `src/triton_kernels.py`：对应 Triton 版本，其中 RMSNorm 和融合版本有分块归约路径；
- `tests/test_correctness.py`：包含非 2 的幂、尾部不对齐、极大值、非连续输入和分块阈值测试；
- `benchmarks/run_bench.py`：warmup、多次重复、中位数、带宽和消融 JSON；
- `integration/vllm_patch.py`：可恢复的 vLLM monkey-patch 骨架；
- `benchmarks/component_share.py`：估算 RMSNorm/SwiGLU 在 Qwen2.5-7B 前向中的时间占比。

这些代码先作为研究工作台，不自动替换 T1 的 `baseline.py`。

## 优先级

### P0：先把现有算子跑通

在目标 AMDGPU/DCU 镜像中确认 Triton 版本、PyTorch 版本、设备后，按这个顺序跑：

```bash
python kernels/tests/test_correctness.py
python kernels/benchmarks/run_bench.py
python kernels/benchmarks/component_share.py
```

保存设备、DTK/ROCm、Triton、PyTorch、commit、warmup、重复次数和 JSON 原始结果。若官方 DCU Triton 与当前实现不兼容，先记录编译错误和算子覆盖范围，不要用 CUDA T4 数据代替 DCU 成绩。

### P1：优先接入两个高频融合算子

先验证：

1. `Qwen2RMSNorm.forward`；
2. vLLM `SiluAndMul.forward`。

它们在每层重复出现、访存占主导、接口相对稳定，适合做第一批端到端实验。接入前必须分别完成：

- BF16/FP16 与 PyTorch 参考的误差检查；
- batch/token 数覆盖 1、32、128、512、2048；
- vLLM patch 前后相同 prompts 的逐 token 对齐；
- eager 和编译路径分别记录，不能把编译失败隐藏在结果里。

### P2：QKV 切分 + RoPE 融合

这条路径可以减少切分、转置、RoPE 中间张量和 kernel launch，但更依赖 Qwen2/vLLM 的张量布局。先在独立函数上验证 `(B,T,H,D)`、GQA 的 KV 头和非连续输入，再接到真实 attention 模块。任何 layout 改变都必须重新做 token-level 对齐。

### P3：真正改变系统行为的优化

投机解码、KV cache 压缩、decode scheduler、paged KV cache 和自研 attention kernel 属于更高风险方向。它们需要请求级 benchmark，观察 TTFT、TPOT、P50/P95/P99、并发吞吐和峰值显存，不适合在算子 benchmark 尚未稳定时同时推进。

## 每个 T4 方案的验收表

| 阶段 | 必须回答的问题 | 通过条件 |
| --- | --- | --- |
| 参考实现 | 数学定义是什么？ | 与 Qwen2 实际路径一致 |
| 正确性 | 是否改变输出？ | FP16 逐 token 一致；BF16 误差在约定阈值内 |
| 单算子性能 | kernel 是否真的更快？ | warmup 后多次中位数优于对应 PyTorch/原 kernel |
| 热点占比 | 优化是否值得接入？ | profiling 或 component share 证明占比足够高 |
| 端到端 | 整个模型是否变快？ | 相同请求集、batch、dtype、计时边界下吞吐提升 |
| 稳定性 | 是否只在一个形状有效？ | 长度、batch、dtype 和并发扫描没有明显回退 |
| 可复现 | 别人能否重跑？ | 命令、环境、commit 和原始 JSON 齐全 |

## T4 实验矩阵

第一轮只改变一个变量：

| 组别 | 运行时 | 优化 | batch/token | 目的 |
| --- | --- | --- | --- | --- |
| K0 | PyTorch | 原始算子 | 1/32/128/512/2048 | 参考 |
| K1 | Triton | RMSNorm | 同 K0 | 单算子收益 |
| K2 | Triton | Add+RMSNorm 融合 | 同 K0 | 访存融合收益 |
| K3 | Triton | SiLU+Mul 融合 | 同 K0 | MLP 激活收益 |
| K4 | vLLM | K1+K3 patch | 并发 1/2/4/8/16/32 | 端到端收益 |
| K5 | Triton | QKV+RoPE 融合 | 512/1024/2048 | attention 小算子收益 |

K4 是决定是否继续投入的关键。如果 K1/K3 单算子很快但 K4 没有提升，原因通常是矩阵乘或 attention 占主导，应转向 profiling、KV cache 或调度，而不是继续堆小 kernel。

## AMDGPU/DCU 注意事项

- `torch.cuda` 是 ROCm 下的兼容命名，不能据此假设 CUDA Triton binary 一定能在 DCU 工作；必须在目标镜像实际编译和运行。
- `triton-3.5.1+das...` 等官方 Triton 与 PyPI Triton 不是同一个兼容目标，环境版本要写入结果 JSON。
- 不能用 Google Colab T4 的加速比推断海光 DCU 的加速比；Colab 数据只能证明算法方向和参考实现。
- 第一次运行包含 Triton 编译开销，不能混入 steady-state 中位数；编译缓存命中与否要单独记录。
- vLLM monkey-patch 是可逆实验入口，不应直接改写 T1 官方 baseline；patch 前后要能恢复原实现。

## 最终报告应包含

1. 热点 profiling 截图或统计；
2. 每个 kernel 的参考公式、布局和融合前后访存路径；
3. 正确性阈值和所有失败形状；
4. 单算子中位数、带宽利用率和端到端吞吐；
5. 在 DCU 实际环境中的回退情况、编译限制和复现命令；
6. 为什么某个方案没有继续采用。

推荐最终方案只保留能在同一 DCU 环境、同一 token contract 下重复得到收益的组件。
