# T1 代码解构

## 执行链路

`baseline.py` 的数据流是：读取 JSONL -> 建立 tokenizer/model -> 使用 chat template 得到 input IDs -> 按原顺序或 token 长度组成 batch -> 左侧 padding -> `model.generate` 贪心生成 -> 按原始 case 索引恢复顺序 -> 去掉 EOS 后的 padding -> 记录 token、文本和计时 -> 写入结果 JSON。

## 文件职责

- `baseline.py`：准备阶段的可重复推理和性能记录入口。
- `t1/core.py`：数据校验、结果摘要、EOS 截断和 token 级对比；不依赖模型。
- `t1/core.py`：还提供 `make_batch_indices` 和 `padding_stats`，用于验证长度排序不改变 case 顺序，并量化静态 batch 的 padding 浪费。
- `evaluate.py`：比较两个结果 JSON 的 contract、输入 token 和输出 token。
- `tests/test_core.py`：验证短输出、EOS、乱序、重复 ID 和首个差异定位。
- `data/smoke.jsonl`：不含敏感数据的本地冒烟集。

## 为什么左侧 padding

Decoder-only 模型从 batch 的最后一个有效位置继续生成。左侧 padding 让不同长度输入的最后一个有效 token 对齐，并通过 `attention_mask` 屏蔽 padding。右侧 padding 会让生成位置落在 padding 上，容易造成错误结果。

## 结果 contract

结果中固定保存模型身份、数据集摘要、解码参数、EOS/PAD ID 和输入 token。比较时先检查 contract，再按 case ID 比较 input/output token。这样可以区分“模型真的不同”和“评测配置被改了”。

## 计时边界

当前准备版统计已预 tokenized 的常驻输入，从第一次 `generate` 前到所有 batch 完成，并在 CUDA 上同步前后设备；不包含模型加载、tokenize、decode。远程正式脚本若定义不同，报告中必须以官方边界为准。

## 长度分桶

默认不排序，保证历史命令的 batch 组成完全稳定。增加 `--length-bucket` 后，程序按输入 token 长度稳定排序，再按 `--batch-size` 切分；模型返回后用原始索引写回 `generated`，所以结果 JSON 的 `outputs` 仍与数据集顺序一致。`batching` 字段记录 `input_tokens`、`padded_input_tokens` 和 `padding_waste_ratio`，便于把吞吐变化和 padding 浪费联系起来。
